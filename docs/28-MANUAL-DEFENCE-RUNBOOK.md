# FixPoint — ручной прогон перед защитой Module 4

> **Срок:** четверг, 19 ноября 2026.  
> **Назначение:** короткий повторяемый сценарий демонстрации реального приложения.  
> **Важно:** использовать только локальные seed-аккаунты. Пароль и инструкции входа брать из README и локального `.env`; не переносить секреты в этот файл.

## 1. Подготовка

1. Запустить проект по разделу Docker Compose в `README.md`.
2. Открыть `http://localhost:8080/health`. Ожидается HTTP 200 и доступная БД.
3. Убедиться, что миграции и seed завершились без ошибок.
4. Подготовить отдельные сессии браузера/инкогнито для клиента, администратора и мастера. Не переключать роли в одной сессии без выхода.
5. Открыть GitHub Actions и проверить, что CI, Browser Visual QA и source audit относятся к последнему HEAD ветки `qa/browser-visual-capture`.

## 2. Демонстрационный основной сценарий

### Шаг A — публичная часть

- Открыть главную, каталог, карточку услуги, «О сервисе» и контакты.
- Убедиться, что услуги и категории отображаются из MySQL, а не только из статического HTML.
- Открыть сайт на ширине 360–390 px и на desktop.

Ожидаемый результат: публичные страницы доступны без авторизации, ссылки каталога открывают соответствующие страницы услуг.

### Шаг B — клиент создаёт заявку

Войти как `customer.kovalev@fixpoint.test` (пароль локального seed указан в README).

- Открыть «Новая заявка».
- Выбрать тип устройства, например ноутбук.
- Выбрать/ввести бренд и модель.
- Выбрать услугу, указать описание проблемы и контакт.
- Отправить форму.
- Зафиксировать номер новой заявки и открыть её карточку.
- Проверить, что заявка появилась в списке клиента, а первая запись истории имеет статус «Новая».

Ожидаемый результат: сервер создаёт заявку и стартовую запись истории; пользователь перенаправляется на карточку своей заявки.

### Шаг C — администратор назначает мастера

В отдельной сессии войти как `admin@fixpoint.test`.

- Открыть реестр заявок и найти заявку по её номеру.
- Открыть назначение мастера.
- Выбрать активного мастера `master.ivanov@fixpoint.test` и сохранить.
- Вернуться в реестр и убедиться, что имя мастера отображается.

Ожидаемый результат: назначение сохраняется на сервере. В списке выбора нет клиентов и неактивных пользователей.

### Шаг D — мастер проводит диагностику

В отдельной сессии войти как `master.ivanov@fixpoint.test`.

- Открыть очередь мастера и найти назначенную заявку.
- Открыть рабочую карточку.
- Сначала перевести заявку из `new` в `accepted`.
- Перевести заявку в `diagnostics`.
- Заполнить результат диагностики, ориентировочную стоимость и дату готовности.
- Сохранить диагностику.
- Перевести заявку в `awaiting_customer_approval` через разрешённые действия интерфейса.
- Добавить обычный комментарий.
- Добавить внутреннюю заметку и проверить, что она помечена как внутренняя.

Ожидаемый результат: изменения сохраняются, а история содержит события смены статуса.

### Шаг E — клиент принимает смету

Вернуться в клиентскую сессию и обновить карточку заявки.

- Проверить наличие диагностики и сметы.
- Проверить, что внутреннюю заметку мастера клиент не видит.
- Согласовать смету.

Ожидаемый результат: заявка переходит в `repairing`, клиент видит публичные комментарии и историю, но не внутренние заметки.

### Шаг F — завершение

Вернуться в сессию мастера.

- Перевести заявку в `ready_for_pickup`.
- Перевести заявку в `completed`.
- Обновить карточку и историю.

Ожидаемый результат: заявка завершена, все переходы отражены в истории, терминальная заявка доступна только для чтения.

## 3. Обязательные негативные проверки

Проверить хотя бы следующие сценарии:

| Проверка | Действие | Ожидаемый результат |
|---|---|---|
| Гость → админка | Открыть `/admin` без входа | Redirect на login |
| Клиент → админка | Открыть `/admin/requests` | 403 |
| Мастер → чужая заявка | Открыть ID заявки, назначенной другому мастеру | 404 |
| Клиент → чужая заявка | Открыть ID заявки другого клиента | 404 |
| Клиент → внутренняя заметка | Отправить комментарий с `is_internal=1` | Флаг игнорируется; клиент не может создать внутреннюю заметку |
| Неверный переход | Попробовать перескочить через недопустимый статус | Сервер отклоняет изменение |
| CSRF | Отправить изменяющий POST без действительного токена | Запрос отклоняется |
| Терминальная заявка | Попробовать изменить `completed` | Изменение отклоняется |

Не проверять только скрытием кнопки: открыть URL напрямую или отправить запрос. Защита должна работать на сервере.

## 4. Административный блок

Под администратором показать:

- глобальный реестр заявок, поиск, фильтры, сортировку и пагинацию;
- назначение мастера;
- список пользователей и редактирование роли/активности;
- список услуг, создание/редактирование и публикацию;
- категории и их активность;
- статистику;
- редактирование публичного блока «О сервисе».

Для CRUD не обязательно создавать много новых записей на защите. Достаточно открыть существующие данные, показать форму и продемонстрировать одну безопасную операцию на тестовой записи, затем вернуть исходное значение.

## 6. Границы результата

Не демонстрировать как готовые функции приватные фото-вложения, live chat, push-уведомления, автоматический подбор мастера, AI-триаж или публичный deployment: они не входят в подтверждённую реализацию текущего PR.

**Фиксация результата ручного прогона:** после выполнения чек-листа записать дату, браузер/устройство, тестовые роли, номер заявки и обнаруженные дефекты. Если тест выполняется не человеком в браузере, не отмечать этот раздел как ручной.
