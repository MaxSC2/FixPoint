## 2. Найденные и исправленные дефекты

### 2.1 P0 — обход согласования сметы клиентом (D1)

**Дефект.** Мастер мог провести заявку из `diagnostics` сразу в `repairing`, минуя смету и решение
клиента, а затем довести её до `completed`. Клиент не участвовал, стоимость нигде не фиксировалась.

**Воспроизведение (до исправления).** HTTP-проба на изолированной БД:

```
new → accepted → diagnostics          (штатные переходы)
POST /technician/requests/2/status  status=repairing   -> HTTP 302
  статус заявки: repairing|NULL        <- сметы нет, клиент не спрашивали
POST .../status status=ready_for_pickup -> HTTP 302   (статус меняется)
POST .../status status=completed       -> HTTP 302   (статус меняется)
```

**Причина.** Матрица `RequestStatusService::TRANSITIONS` содержала `diagnostics → repairing` и
`diagnostics → awaiting_parts`. Сервисный предохранитель срабатывал только когда смета **уже была**
сохранена (`RequestService.php`, блок «$hasEstimate && …»), а SQL-предicat в
`RequestRepository::transitionStatus` прямо разрешал этот переход при `estimated_cost IS NULL`.
То есть запрет срабатывал ровно в том случае, когда обходить было нечего.

Дополнительно: переход `awaiting_parts → repairing` при наличии сметы блокировался тем же правилом,
то есть механика «ремонт приостановлен до запчасти → продолжение» была фактически нерабочей.

**Исправление.** Три уровня, чтобы инвариант нельзя было обойти ни через интерфейс, ни прямой
POST, ни гонкой запросов:

1. `app/Services/RequestStatusService.php` — из `diagnostics` убраны `repairing` и `awaiting_parts`;
   в `awaiting_parts` оставлен только `repairing` (возврат согласованного ремонта).
2. `app/Services/RequestService.php` — вход в `repairing` требует сохранённой сметы; для
   `diagnostics` с готовой сметой сохраняется прежнее понятное сообщение о необходимости
   отправить смету клиенту.
3. `app/Repositories/RequestRepository.php` — условный `UPDATE` внутри транзакции с
   `SELECT … FOR UPDATE`: `diagnostics → repairing` отсекается условием, а любой вход в `repairing`
   требует `estimated_cost IS NOT NULL`.

**Проверка после исправления.** Та же проба: `diagnostics → repairing` отклоняется, статус остаётся
`diagnostics`; сценарий «согласовали → ремонт → пауза на запчасти → продолжение» работает.

### 2.2 P1 — все карточки услуг показывали общую иконку

**Дефект.** `app/Views/components/service-card.php` читал `$service['category_slug']`, но
`CatalogService::mapService()` отдаёт категорию вложенной структурой (`$service['category']['slug']`).
Ключ `category_slug` в массиве карточки отсутствовал, поэтому `$iconVariant` всегда был `general`,
а атрибут `data-category-slug` — пустым. На рабочем дереве: `general × 10` из 10 карточек.

**Исправление.** Чтение slug из вложенной структуры с сохранением обратной совместимости
(`$service['category']['slug'] ?? $service['category_slug'] ?? ''`).

**Проверка.** После исправления: `computers × 5, diagnostics × 2, smartphones × 2, network × 1`;
`data-category-slug` заполнен (`computers-laptops | smartphones-tablets | network | diagnostics`).

### 2.3 P1 — отклонённый переход статуса не показывался пользователю

**Дефект.** Ошибка смены статуса хранилась в поле `status`, а карточка мастера выводила ошибки полей
только внутри формы смены статуса. Когда переход недостижим, форма не рендерится — и сообщение
«Этот переход статуса недопустим.» исчезало целиком: мастер нажимал «Сохранить» и не видел ответа.

**Исправление.** `app/Views/pages/technician/requests/show.php` — ошибка статуса выводится общим
блоком-предупреждением, даже если форма смены статуса не показана.

### 2.4 P2 — области нажатия в административской таблице

**Дефект.** Ссылка «Назначить» в реестре заявок имела высоту 16px, круглая стрелка — 26×26.
Это ровно тот дефект, который числился в `docs/37-MODULE4-AUDIT-CHECKPOINT-2026-11-18.md:106`.
Класс `.admin-row-assign` был добавлен в разметку, но правил для него в CSS не появилось.

**Исправление.** `public/assets/css/app.css` — оформлена кнопка «Назначить» с настоящей областью
нажатия (32px на десктопе, 44px на мобильном), стрелка увеличена до 32×32.

### 2.5 P2 — мобильные области нажатия ниже 44px

**Дефект.** В узких брейкпоинтах `.nav-toggle` ужимался до 40–41px, кнопки шапки и фильтров — до
39–42px, ссылки футера — до 22px. Проектный стандарт для пальцевых целей — 44px
(`docs/18-UI-01-IMPLEMENTATION-REPORT.md:49`).

**Исправление.** Один блок в конце `public/assets/css/app.css` приводит все эти элементы к 44px
на ширине до 640px, вместо того чтобы править каждый дубликат правила по отдельности.

### 2.6 P2 — ошибка PHP на этапе загрузки конфигурации

**Дефект.** `public/index.php` подключал `app/bootstrap.php` до того, как выставлялся
`display_errors=0`. Ошибка конфигурации (например, неверный `APP_TIMEZONE`) на SAPI с включённым
`display_errors` печатала бы текст исключения и стек-трейс с абсолютными путями.

**Исправление.** `ini_set('display_errors', '0')`, `display_startup_errors` и `log_errors` выставлены
до подключения bootstrap.

### 2.7 P2 — одинаковое время ответа при входе

**Дефект.** `AuthService::attempt()` возвращался сразу, если email не найден или аккаунт неактивен —
без `password_verify`. Для существующего аккаунта выполнялась проверка bcrypt. По времени ответа
можно было определить, зарегистрирован ли адрес.

**Исправление.** `app/Services/AuthService.php` — в ветке «неизвестный/неактивный аккаунт» выполняется
проверка против фиксированного bcrypt-хэша (`DUMMY_PASSWORD_HASH`), стоимость веток сравнялась.

### 2.8 P2 — «Комментарий к переходу» не помечен как видимый клиенту

**Дефект.** Текст из поля «Комментарий к переходу» попадает в историю заявки и показывается клиенту,
но подпись об этом не говорила. Служебные заметки мастер мог принять за внутренние (для внутренних
есть отдельный механизм — комментарий с отметкой «Внутренняя заметка»).

**Исправление.** `app/Views/pages/technician/requests/show.php` — подпись прямо называет видимость,
плейсхолдер подсказывает, где писать служебные заметки. Изменение схемы БД не потребовалось.

### 2.9 P2 — 404 в консоли браузера на каждой странице

**Дефект.** Запрос `/favicon.ico` возвращал 404 — единственная ошибка в консоли на всех страницах.

**Исправление.** `app/Views/layouts/header.php` — добавлена ссылка на SVG-иконку в виде data-URI
(знак бренда). Новый файл не добавлялся. После исправления консоль чиста.

## 5. Проверка интерфейса

Структурная проверка выполнена на 25 страницах под четырьмя ролями, вёрстка — на 1440×900 и
на ширине 390px (фактически 487 CSS-пикселей из-за масштаба окна).

**Найдено и исправлено:** области нажатия (раздел 2.4 и 2.5), ошибка 404 в консоли (раздел 2.9).

**Проверено и признано корректным:**

- горизонтального переполнения нет ни на одной странице: `scrollWidth` равен ширине вьюпорта;
  широкая таблица реестра помещена в обёртку с `overflow-x: auto` и помечена `role="region"` с
  `aria-label` и `tabindex="0"` — это правильный паттерн, а не обрезка;
- на всех страницах ровно один `<h1>`; `lang="ru"` задан;
- нет дублирующихся `id`; у всех `<img>` есть `alt`;
- у всех интерактивных элементов есть доступное имя; у всех полей есть связанный `label`;
- у клиента, мастера и администратора на публичных страницах нет ссылок на `/register` и `/login`;
- консоль браузера чиста на всех проверенных страницах;
- ошибок PHP (Fatal/Warning/Exception) в логах нет.

## 8. Оставшиеся ограничения

1. **`final_cost` не записывается приложением.** Осознанное ограничение MVP
   (`docs/00-URGENT-MODULE-4-DEADLINE-2026-11-19.md:332`), не дефект. В клиентской карточке итоговая
   стоимость остаётся «Не определена». Новая финансовая логика не внедрялась.
2. **Часовые пояса.** Метки времени (`created_at`, `updated_at`, события истории) MySQL пишет в UTC
   (`SET time_zone = '+00:00'`), а `estimated_ready_at` PHP записывает в локальном времени приложения.
   Представления выводят сохранённое значение как есть, поэтому «Ориентир готовности» и события
   истории расходятся на смещение часового пояса, а обе метки показываются в базе как локальные.
   Приведение к единой базе требует миграции данных и правки существующих строк — в этом спринте
   не выполнялось, чтобы не менять демонстрационные данные.
3. **Ограничение по частоте попыток входа и блокировка учётной записи не реализованы.** Вход
   защищён CSRF, `password_hash`/`password_verify`, сменой ID сессии и выравниванием времени ответа,
   но счётчика неудачных попыток и временной блокировки нет. Требует изменения схемы `users`.
4. **Смена пароля пользователем и сброс пароля администратором отсутствуют.** `UserRepository::updatePasswordHash`
   используется только для автоматического пере-хеширования. Отсутствующий путь — пробел в
   функциональности, а не дефект безопасности.
5. **Контактные данные остаются заглушками**, пока не заданы `CONTACT_ADDRESS`, `CONTACT_PHONE`,
   `CONTACT_EMAIL`. Выдуманные адреса и телефоны не подставлялись.
6. **Критерий приёмки «у списков есть состояние загрузки» не закрыт.** Приложение рендерится на
   сервере, асинхронной загрузки списков нет, состояния `loading` не существует. Критерий из
   `docs/08-ACCEPTANCE-CRITERIA.md:34` для этого приложения неприменим.
7. **Docker Compose проверен только в CI**, локально Docker недоступен.
8. **Два подряд открытых PR-черновика** (#31, #30 и другие) не сливались: по условию задания
   изменения в GitHub не публикуются.
