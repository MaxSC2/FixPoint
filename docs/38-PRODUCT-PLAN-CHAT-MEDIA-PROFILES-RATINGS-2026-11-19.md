## 1. Короткий ответ: чем чат отличается от комментария

**Комментарий — это запись в деле.** Он нужен, чтобы оставить след: зафиксировать факт, объяснить решение, сохранить внутреннюю заметку. Комментарий не требует ответа и не является диалогом. Он живёт в истории заявки и может быть внутренним.

**Чат — это разговор.** Он нужен, когда нужен ответ: уточнить детали, попросить фото, согласовать время, быстро решить вопрос. У чата есть собеседник, непрочитанные сообщения, вложения и отдельный вход в интерфейсе.

| Критерий | Комментарий | Чат |
|---|---|---|
| Смысл | Запись в журнале заявки | Диалог двух сторон |
| Ждёт ответа | Нет | Да |
| Кто пишет | Мастер, администратор; клиент — только в legacy-режиме | Клиент, назначенный мастер, поддержка |
| Видимость | Внутренняя или опубликованная клиенту | Все участники заявки |
| Вложения | Не в первой версии | Фото и файлы |
| Непрочитанные | Нет | Да, счётчик и бейдж |
| Вход | Внутри карточки заявки | Отдельный раздел «Сообщения» + карточка заявки |
| Роль в аудите | Часть истории и обоснований | Оперативная коммуникация, не заменяет журнал |

**Правило для интерфейса:** если человеку нужно оставить след — он пишет комментарий; если нужно получить ответ — он пишет в чат. На одном экране не должно быть двух конкурирующих полей «напишите что-нибудь».

### 2.1. Технические ограничения, которые важно учесть

- `Request` не принимает `$_FILES`: для загрузки нужен отдельный value object `UploadedFile` и аккуратное расширение `Request::fromGlobals()`.
- В локальном PHP включены `fileinfo` и `pdo_mysql`, но **нет `gd`/`imagick`**. В Dockerfile тоже установлены только `pdo_mysql` и `mbstring`. Значит, перекодирование изображений и генерация миниатюр требуют добавления GD в Docker; для локального демо нужен безопасный fallback.
- `Migrator` выполняет **один SQL-запрос на файл** и запрещает менять уже применённые миграции. Новые таблицы и `ALTER TABLE` оформляются отдельными файлами.
- В `storage/` сейчас только `logs` и `sessions`. Приватные вложения должны лежать вне `public/`, например `storage/private/`.
- `Controller::viewData()` — правильное место для глобального счётчика непрочитанных, чтобы бейдж в шапке не дублировать в каждом контроллере.

## 3. Продуктовое решение

1. **Чат становится единственным двусторонним каналом** между клиентом, мастером и поддержкой.
2. **Комментарии становятся журналом заявки.** Внутренние заметки видят только сотрудники; опубликованные пояснения клиент видит в режиме чтения. Клиент больше не пишет новые комментарии — для этого есть чат.
3. **Оба инструмента связываются действиями-мостами**, чтобы не дублировать друг друга:
   - «Зафиксировать в журнале» на сообщении чата — создаёт комментарий со ссылкой на исходное сообщение.
   - «Отправить клиенту» на внутренней заметке — публикует её как официальное пояснение (с подтверждением).
4. **Фото — одна подсистема вложений** для первичной заявки и для сообщений чата, а не два разных загрузчика.
5. **Профиль мастера — публичная витрина компетенций**, а не просто учётная запись. Рейтинг — следствие завершённых заявок, а не отдельная игра.
6. **«Доска почёта» заменяет «Популярные услуги» на главной.** Услуги уже перечислены выше в блоках направлений и доступны в каталоге; доверие к сервису сильнее формируют люди и реальные отзывы.

## 4. Как сделать чат отдельной и полезной функцией

### 4.1. Отдельный раздел «Сообщения»

- `GET /messages` — список диалогов пользователя.
- `GET /messages/{id}` — отметить прочитанным и перенаправить в карточку заявки к якорю `#chat`.
- `POST /messages/{id}/read` — отметить прочитанным без перехода (для badge/polling).
- В шапке — ссылка «Сообщения» с числом непрочитанных.
- На мобильном — пункт «Чаты» в нижней навигации вместо «Услуги» (услуги остаются в меню и на главной).

Список диалога показывает: номер заявки, устройство, собеседника, последнее сообщение, время, бейдж непрочитанных. Сортировка — по времени последнего сообщения. Фильтр «Только непрочитанные».

### 4.2. Непрочитанные сообщения

Новая таблица:

```sql
CREATE TABLE chat_reads (
    request_id BIGINT UNSIGNED NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL,
    last_read_message_id BIGINT UNSIGNED NOT NULL DEFAULT 0,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (request_id, user_id),
    CONSTRAINT fk_chat_reads_request FOREIGN KEY (request_id) REFERENCES repair_requests (id),
    CONSTRAINT fk_chat_reads_user FOREIGN KEY (user_id) REFERENCES users (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

Непрочитанные = сообщения с `id > last_read_message_id`, где автор не текущий пользователь. Открытие карточки заявки обновляет `last_read_message_id`. Счётчик для шапки кэшируется в сессии на один запрос, чтобы не считать его дважды.

### 4.3. Вложения в чате

- В сообщении может быть текст, до 5 изображений, или только изображения.
- Для сообщения-вложения `request_messages.body` становится nullable (отдельная миграция).
- В ленте — сетка превью, клик открывает полноразмерное изображение через авторизованный маршрут.
- Ограничения: JPEG/PNG/WebP, до 8 МБ на файл, до 40 Мп, до 10 файлов на заявку в первой версии.

### 4.4. Что не делать в чате

- Не обещать real-time, push, e-mail или SMS, пока этих каналов нет.
- Не делать публичные чаты, личные сообщения вне заявки, переписку между клиентами.
- Не позволять чату менять статус заявки или смету. Это делает мастер через существующий workflow.
- Не смешивать внутренние заметки и сообщения чата в одном списке.

### 5.1. Связи

- Заявка — владелец всех вложений (`request_attachments.request_id`).
- Сообщение чата — необязательный контекст вложения (`message_id`); фото, приложенные при создании заявки, имеют `message_id = NULL`.
- Аватар — ключ в приватном хранилище, а не публичный URL.
- Отзыв — ровно один на завершённую заявку, автор — только владелец заявки.

## 6. Слои и маршруты

### 6.1. Новые классы

| Слой | Классы |
|---|---|
| Controllers | `ChatController`, `AttachmentController`, `ProfileController`, `MasterController`, `ReviewController`, `AdminReviewController` |
| Services | `ChatService`, `AttachmentService`, `ImageValidator`, `ProfileService`, `ReviewService`, `RatingService` |

| Policies | `ChatPolicy`, `AttachmentPolicy`, `ReviewPolicy`, `ProfilePolicy` |

`RequestService` не разрастается: чат и вложения уходят в отдельные сервисы. Существующие методы `chatMessages()`/`postMessage()` можно оставить как тонкие делегаты на переходный период, затем удалить.

### 6.2. Маршруты

```php
// Чат
$router->get('/messages', [ChatController::class, 'index'], [AuthMiddleware::class]);
$router->get('/messages/{id:\d+}', [ChatController::class, 'open'], [AuthMiddleware::class]);
$router->post('/messages/{id:\d+}/read', [ChatController::class, 'read'], [AuthMiddleware::class]);

// Вложения
$router->get('/requests/{id:\d+}/attachments/{attachmentId:\d+}',
    [AttachmentController::class, 'show'], [AuthMiddleware::class]);

// Профиль и мастера
$router->get('/account/profile', [ProfileController::class, 'edit'], [AuthMiddleware::class]);
$router->post('/account/profile', [ProfileController::class, 'update'], [AuthMiddleware::class]);
$router->post('/account/profile/avatar', [ProfileController::class, 'uploadAvatar'], [AuthMiddleware::class]);
$router->post('/account/profile/avatar/delete', [ProfileController::class, 'deleteAvatar'], [AuthMiddleware::class]);
$router->get('/masters', [MasterController::class, 'index']);
$router->get('/masters/{id:\d+}', [MasterController::class, 'show']);

// Отзывы
$router->post('/requests/{id:\d+}/review', [ReviewController::class, 'store'], [AuthMiddleware::class]);
$router->get('/admin/reviews', [AdminReviewController::class, 'index'], $adminOnly);
$router->post('/admin/reviews/{id:\d+}/moderate', [AdminReviewController::class, 'moderate'], $adminOnly);
```

### 6.3. Права

- `ChatPolicy`: клиент — только своя заявка; мастер — только назначенная; админ — любая. Проверка повторяется на каждом чтении и записи, а не только на маршруте.
- `AttachmentPolicy`: доступ наследуется от заявки; имя файла и путь никогда не принимаются от клиента.
- `ReviewPolicy`: отзыв только владелец, только статус `completed`, только один раз.
- `ProfilePolicy`: пользователь редактирует только свой профиль; админ может скрыть публичность и отредактировать служебные поля.

## 7. Вложения: безопасность и хранение

### 7.1. Хранение

```text
storage/private/requests/{requestId}/{32-hex}.{ext}
storage/private/avatars/{userId}/{32-hex}.{ext}
```

- `storage/private/` добавляется в `.gitignore`.
- В Docker — создать каталог и выдать права `www-data`.
- Публичного URL нет. Выдача — только через контроллер с проверкой прав.

### 7.2. Проверка файла

1. `is_uploaded_file()` и код ошибки `UPLOAD_ERR_OK`.
2. Размер: не больше 8 МБ; количество: не больше 5 за одно сообщение и 10 на заявку.
3. `finfo_file()` — реальный MIME, не `$_FILES['type']`.
4. `getimagesize()` — декодирование заголовка, ширина/высота, лимит 40 Мп.
5. Разрешены только `image/jpeg`, `image/png`, `image/webp`. SVG, HTML, PHP, архивы отклоняются.
6. Расширение вычисляется из MIME, а не из имени файла.
7. Имя — `bin2hex(random_bytes(16))`; исходное имя хранится только в БД для подписи.
8. Права файла — `0640`, каталог — `0750`.

### 7.3. Выдача

- Проверка сессии и доступа к заявке.
- `Content-Type` из БД, `Content-Length`, `X-Content-Type-Options: nosniff`.
- `Cache-Control: private, max-age=300`, без публичного кэша.
- `Content-Disposition: inline; filename="..."` с безопасным именем.
- При отсутствии файла или чужих правах — `404`, без утечки факта существования.

### 7.4. EXIF и перекодирование

- В Docker добавить GD (`libjpeg-dev`, `libpng-dev`, `libwebp-dev`, `docker-php-ext-install gd`).
- При наличии GD: перекодировать JPEG/PNG/WebP, уменьшать до 2000 px по длинной стороне, удалять EXIF/GPS, генерировать превью 480 px.
- Без GD (локальное демо): сохранять оригинал в приватном хранилище, но не обещать удаление EXIF; это явно указать в README и в тестах.
- Проверять `imagecreatefromstring()` на «decompression bomb» через лимит пикселей до декодирования.

### 7.5. UX загрузки

- На создании заявки: блок «Фотографии устройства» с `enctype="multipart/form-data"`, drag-and-drop, превью, удаление, счётчик.
- В чате: кнопка «Прикрепить фото», превью до отправки, прогресс/disabled на время загрузки.
- Ошибки — рядом с полем, без потери уже введённого текста.
- На карточке — галерея с подписями «Клиент»/«Мастер» и датой.

## 8. Профили и аватары

### 8.1. Что редактирует пользователь

- Имя (2–160 символов), телефон (до 32), аватар.
- Мастер дополнительно: заголовок (до 120), описание (до 1000), опыт с (дата), специализации (до 8 тегов), публичность профиля.
- Клиент: имя, телефон, аватар. Описание и специализации скрыты.

### 8.2. Аватар

- Загрузка через тот же `AttachmentService`/`ImageValidator`, отдельный каталог.
- Кроп по центру до квадрата 512×512 (GD); без GD — исходник, но с проверкой и лимитами.
- В шапке: `<img>` при наличии, иначе текущие инициалы. Alt — имя пользователя.
- Удаление аватара возвращает инициалы.
- Не хранить аватар в `public/` и не отдавать по прямому пути.

### 8.3. Публичная страница мастера

`GET /masters/{id}`:

- аватар, имя, заголовок, описание;
- теги специализаций (устройства и навыки);
- средний рейтинг, число отзывов, число завершённых заявок;
- последние опубликованные отзывы;
- кнопка «Создать заявку» (не запись на приём и не выбор мастера клиентом);
- скрыть страницу, если `is_public = 0` или пользователь неактивен.

Админ видит те же данные в карточке пользователя и может управлять публичностью и тегами.

## 9. Рейтинг и «Доска почёта»

### 9.1. Правила отзыва

- Только владелец заявки.
- Только статус `completed`.
- Одна заявка — один отзыв.
- Оценка 1–5, текст до 1500 символов, необязательный.
- Публикация автоматическая, администратор может скрыть отзыв при нарушении правил.
- Нельзя оценить себя, чужую заявку, незавершённую заявку; повторный отзыв отклоняется.

### 9.2. Агрегаты

- `rating_avg = AVG(rating)` по опубликованным отзывам.
- `rating_count = COUNT(*)`.
- Для главной — взвешенный рейтинг, чтобы один отзыв не выводил мастера на первое место:

```text
weighted = (avg * count + global_avg * 5) / (count + 5)
```

где `global_avg` — средний рейтинг по всем опубликованным отзывам (при отсутствии отзывов — 4.5 как нейтральный старт, но это значение не показывается как реальный рейтинг).

- На публичной странице показывать честно: «Рейтинг 4.8 · 12 отзывов», а не только округлённую звезду.

### 9.3. Главная: вместо «Популярных услуг»

Блок 04 заменяется на **«Доска почёта»**:

- 3 мастера с лучшим взвешенным рейтингом и минимум 3 опубликованными отзывами;
- аватар, имя, специализации, рейтинг, число завершённых заявок, одна цитата из отзыва;
- ссылка «Все мастера» → `/masters`;
- если отзывов ещё нет — не выдумывать рейтинг: показать «Доска почёта формируется» и список активных мастеров без звёзд.

«Популярные услуги» не удаляются из продукта: они остаются в каталоге и могут быть compact-строкой ниже, но не занимают центральный доверительный блок главной.

## 11. Критерии приёмки

### 11.1. Сквозной сценарий

1. Клиент создаёт заявку и прикладывает 2 фото; фото видны в карточке.
2. Мастер открывает заявку, видит фото, пишет в чат и прикладывает своё фото.
3. У клиента появляется бейдж непрочитанного; он открывает «Сообщения», видит диалог, сообщение помечается прочитанным.
4. Мастер оставляет внутреннюю заметку — клиент её не видит ни в HTML, ни в API.
5. Мастер публикует официальное пояснение — клиент видит его в журнале, но не может ответить комментарием (отвечает в чате).
6. Заявка завершается; клиент ставит 5 звёзд и текст.
7. Рейтинг мастера обновляется, отзыв появляется на публичной странице, мастер попадает на доску почёта при достаточном числе отзывов.
8. Мастер загружает аватар; он виден в шапке, чате и публичном профиле.
9. Чужой пользователь получает `404` на вложение, диалог, отзыв и профиль, если профиль скрыт.

### 11.2. Безопасность

- [ ] Ни один файл не отдаётся по прямому пути из `public/`.
- [ ] SVG, HTML, PHP и архивы отклоняются.
- [ ] Имя и MIME от клиента не используются как доверенные.
- [ ] Внутренние заметки не попадают в клиентские view-модели.
- [ ] CSRF обязателен для всех POST.
- [ ] Лимиты размера, количества и пикселей работают на сервере.
- [ ] Ошибки не раскрывают путь к файлу и существование чужой заявки.

### 11.3. UX

- [ ] На карточке заявки нет двух конкурирующих полей ввода.
- [ ] На мобильном чат и галерея работают без горизонтальной прокрутки.
- [ ] Кнопка «Прикрепить фото» доступна с клавиатуры.
- [ ] Пустые состояния объясняют, где писать и где смотреть журнал.
- [ ] Нет обещаний push/e-mail/SMS, которых нет в продукте.

## 12. Решения, которые нужно подтвердить

| Вопрос | Рекомендация | Почему |
|---|---|---|
| Оставлять ли клиенту комментарии? | Нет новых; старые читать | Иначе два канала конкурируют |
| Комментарии только внутренние? | Нет: внутренние + опубликованные пояснения | Клиенту нужен официальный след, но не второй чат |
| Переименовывать `request_messages`? | Нет | Логическая граница важнее имени, меньше риска |
| Рейтинг без отзывов на главной? | Не показывать звёзды, показать «формируется» | Не выдумывать доверие |
| Публичные профили мастеров? | Да, только имя/описание/теги/рейтинг | Не раскрывать email/телефон |
| GD в Docker? | Да; локально — fallback | Без GD нет удаления EXIF и превью |
| Real-time чат? | Нет в первой версии | Polling/refresh достаточно, меньше сложности |
| Кто модерирует отзывы? | Автопубликация + скрытие админом | Не тормозить обратную связь |
