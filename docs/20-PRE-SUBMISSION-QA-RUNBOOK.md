# FixPoint — pre-submission QA runbook

**Цель:** провести воспроизводимую проверку перед сдачей. Этот документ — чек-лист ручной проверки, а не утверждение, что все пункты уже пройдены.

## 1. Чистый запуск

- [ ] Проверить, что используется актуальная интеграционная ветка `develop`.
- [ ] Убедиться, что локальный `.env` создан из `.env.example`; секреты не публиковать.
- [ ] Выполнить `docker compose up --build -d`.
- [ ] Дождаться healthy для MySQL и приложения.
- [ ] Открыть `http://localhost:8080/health`, убедиться в HTTP 200 и доступности БД.
- [ ] Проверить логи: `docker compose logs --no-color --tail=200 app db`; не должно быть необработанных исключений миграций/seed.
- [ ] Проверить `docker compose ps`.
- [ ] Зафиксировать commit SHA, ОС, версии Docker/Compose и результат.

## 2. Демонстрационные учётные записи

Пароль seed-пользователей задаётся переменной `SEED_PASSWORD` в локальном `.env`. По умолчанию README указывает `FixPoint!Dev1`. Использовать только локальные демонстрационные данные.

| Роль | Email |
|---|---|
| Администратор | `admin@fixpoint.test` |
| Мастер | `master.ivanov@fixpoint.test` |
| Мастер | `master.smirnova@fixpoint.test` |
| Клиент | `customer.kovalev@fixpoint.test` |
| Клиент | `customer.ivanova@fixpoint.test` |
| Неактивный клиент | `inactive@fixpoint.test` |

- [ ] Проверить вход каждой активной роли.
- [ ] Проверить отказ во входе неактивному пользователю.
- [ ] Проверить logout и невозможность открыть защищённую страницу после выхода.

## 3. Сквозной сценарий — основная демонстрация

Использовать отдельную тестовую заявку, чтобы не испортить исходные seed-данные.

1. **Клиент**
   - [ ] Войти как клиент.
   - [ ] Создать заявку с типом устройства, брендом, моделью и описанием неисправности.
   - [ ] Убедиться, что заявка появилась в списке и открывается.
   - [ ] Добавить публичный комментарий.
2. **Администратор**
   - [ ] Войти администратором.
   - [ ] Найти созданную заявку в общем реестре.
   - [ ] Назначить активного мастера.
   - [ ] Убедиться, что назначение отображается в заявке.
3. **Мастер**
   - [ ] Войти назначенным мастером.
   - [ ] Убедиться, что заявка есть в его очереди.
   - [ ] Открыть карточку и сохранить результат диагностики, стоимость и ожидаемую дату.
   - [ ] Перевести заявку в состояние ожидания согласования.
   - [ ] Добавить внутреннюю заметку.
4. **Клиент**
   - [ ] Вернуться клиентом и открыть ту же заявку.
   - [ ] Убедиться, что смета отображается и доступно решение.
   - [ ] Убедиться, что внутренняя заметка мастера не видна.
   - [ ] Согласовать смету.
5. **Мастер**
   - [ ] Убедиться, что заявка доступна мастеру после согласования.
   - [ ] Перевести её в ремонт, затем в «Готова к выдаче».
6. **Клиент**
   - [ ] Убедиться, что статус и история обновились.
7. **Мастер или администратор**
   - [ ] Завершить заявку, если это предусмотрено текущими разрешениями интерфейса.
   - [ ] Убедиться, что история всех переходов сохранилась.

Если какой-либо переход не предусмотрен текущей матрицей статусов или ролью, не обходить ограничение напрямую в БД: записать фактический результат и передать backend-агенту.

## 4. Проверка доступа и безопасности

- [ ] Клиент A не может получить заявку клиента B подстановкой ID (ожидается 404 согласно контракту).
- [ ] Мастер A не может открыть или изменить заявку, назначенную мастеру B.
- [ ] Клиент не может открыть маршруты мастера или администратора (403/redirect согласно middleware).
- [ ] Мастер не может открыть административные CRUD-маршруты.
- [ ] Гость перенаправляется на вход при открытии защищённого URL.
- [ ] POST без CSRF-токена отклоняется.
- [ ] GET-запрос не меняет состояние.
- [ ] Клиент не может создать внутренний комментарий.
- [ ] В HTML не отображаются SQL, stack trace, секреты и необработанный пользовательский HTML.
- [ ] Регистрация не позволяет самостоятельно выбрать роль администратора или мастера.

## 5. Проверка административных функций

- [ ] Открыть реестр заявок, проверить поиск, фильтры и пагинацию.
- [ ] Создать пользователя; проверить роль и временный пароль.
- [ ] Изменить профиль пользователя и его активность.
- [ ] Создать/изменить услугу и проверить её видимость в публичном каталоге.
- [ ] Создать/изменить категорию и проверить связь с услугами.
- [ ] Проверить, что деактивация мастера не позволяет назначить его на новую заявку.
- [ ] Проверить статистику: числа должны происходить из БД, не из фиктивных констант.

## 6. UI / responsive smoke

Проверить ширины viewport: 360 px, 768 px, 1024 px и 1440 px.

- [ ] Нет горизонтального скролла страницы.
- [ ] Навигация доступна мышью и клавиатурой.
- [ ] Видимый focus у интерактивных элементов.
- [ ] Поля имеют label, ошибки привязаны к полям.
- [ ] Ошибка валидации не стирает введённый текст.
- [ ] Подтверждение отклонения сметы работает; при отключённом JS форма остаётся отправляемой.
- [ ] Таблицы, карточки и длинные тексты не ломают layout.
- [ ] Проверить пустые состояния и сообщения об ошибках.

Сохранить скриншоты минимум для: главной, входа, клиентской заявки, очереди мастера, карточки диагностики, административного реестра, мобильной главной.

## 7. Автоматические проверки и артефакты

Выполнить команды, предусмотренные workflow/README проекта, и приложить фактический вывод:

- [ ] PHP lint.
- [ ] Unit + integration tests.
- [ ] Docker Compose runtime/health/smoke.
- [ ] GitHub Actions на точном commit SHA.
- [ ] Нет незакоммиченных изменений и локальных секретов.

### Формат отчёта

Для каждого пункта указывать одно из состояний: `PASS`, `FAIL`, `BLOCKED`, `NOT RUN`.

Для каждого FAIL/BLOCKED приложить:
- роль и тестовую учётную запись (без пароля);
- URL и шаги воспроизведения;
- ожидаемое и фактическое поведение;
- commit SHA и скриншот/лог без секретов.

## 8. Финальный gate

Не объявлять проект готовым только на основании зелёного CI. Для сдачи нужны одновременно:
- [ ] чистый запуск по README;
- [ ] зелёные автоматические тесты;
- [ ] успешный сквозной сценарий трёх ролей;
- [ ] проверки доступа;
- [ ] скриншоты desktop/mobile;
- [ ] отсутствие критических FAIL;
- [ ] краткий отчёт с commit SHA и ограничениями.
